# 环境复现指南

本文说明如何**从零**在另一台机器上复现出与本仓库完全一致的最小 Qwen3-TTS 环境。
整套流程只需要 `git`、`Python 3.11`、`make`（Windows 见 [Windows说明.md](Windows说明.md)），
以及一次约 840 MB 的依赖下载。

---

## 1. 这套环境到底是什么

先明确「精简」的边界，避免复现时下意识去装多余东西：

| 层 | 用什么 | 不用什么 |
|---|---|---|
| 推理引擎 | `qwentts.cpp`（GGML C++）预编译动态库 | PyTorch、Transformers、ONNX Runtime、llama.cpp |
| Python 绑定 | `qwentts-cpp-python`（ctypes 调用动态库） | modelscope、huggingface-hub、accelerate |
| 音频读写 | `numpy` + 标准库 `wave` | soundfile、librosa、ffmpeg、scipy |
| Web 服务 | 标准库 `http.server` + `queue` | Flask、FastAPI、uvicorn、gunicorn |
| 权重 | Q4_K_M 量化 GGUF（2 个文件） | 原始 safetensors（1.7 GB）、fp32 权重 |

最终 `pip list` 只有 5 项，其中真正需要用户关心的只有 `numpy` 和 `qwentts-cpp-python`：

```
numpy              2.4.6
qwentts-cpp-python 0.5.0+cpu
pip / setuptools / typing_extensions   ← venv 自带或 wheel 附带
```

**为什么能这么小**：`qwentts-cpp-python` 的 wheel 里已经包含编译好的 GGML 动态库，
Python 侧只用 ctypes 调它；`app.py` 只是把生成结果用标准库 `wave` 写成 WAV。
所以完全不需要 Python 深度学习栈。

## 3. 一键复现（推荐）

```bash
git clone https://github.com/EA212/qwen3-tts-minimal.git qwen3-tts-minimal
cd qwen3-tts-minimal
make                       # = make setup + make run
```

`make` 会依次做四件事：

1. `python3 fetch_deps.py` —— 下载并校验 4 个依赖文件（见第 4 节）；
2. `python3 -m venv .venv` —— 建隔离环境；
3. 从 `wheels/` **离线**安装 numpy 与引擎 wheel（`--no-index --no-deps`）；
4. `./start.sh 3000` —— 启动服务。

看到 `[boot] http://0.0.0.0:3000` 和 `[ready] 加载 2.x s，音色 9 个` 即成功。
浏览器打开 <http://localhost:3000>。

### 分步执行（便于排查）

```bash
make deps        # 只下载 + 校验
make venv        # 只建环境
make setup       # deps + venv
make verify      # 生成 audio/verify.wav，确认推理链路通
make run         # 启动服务
```

### 复用已有环境（省 840 MB 下载）

如果这台机器上已有下载好的权重（例如旧项目目录），用 `CACHE` 指向它，
`fetch_deps.py` 会校验后**硬链接**过去，零拷贝、秒级完成：

```bash
make deps CACHE=/path/to/old/qwen3-tts-minimal
make
```

也可直接把旧的 `models/` 和 `wheels/` 拷进新目录，只要文件名和校验值一致就会被跳过。

## 7. 原理与性能基准

### 为什么慢在「结构」而不是「脚本」

Qwen3-TTS 是 12.5 帧/秒 × 16 码本的**自回归**生成，每 1 秒音频要串行解码约 187 次。
所以换更小模型收益有限，真正的提速来自换推理引擎 + 量化 + 流式：

| 后端 | 精度 | 同句生成 | 音频 | RTF |
|---|---|---:|---:|---:|
| 官方 PyTorch | float32 | 76.3 s | 3.36 s | 22.7 |
| 官方 PyTorch | bf16 | 26.5 s | 2.96 s | 8.95 |
| **本仓库 GGML** | **Q4_K_M** | **14.5 s** | **2.96 s** | **4.9** |

比最初快约 5 倍，模型加载从几十秒降到约 2.5 秒，
`synth.py --stream` 的**首包出声约 3.5 秒**（网页为保证最精简仍用整段生成）。

### CPU 配额是硬上限（重要）

实测过一台 `nproc=32` 但 cgroup `cpu.max = 400000/100000`（= 4 核）的机器：
无论开 2 / 8 / 16 / 32 / 48 个线程，实际都只用满 4 核，速度差异不到 1%，
期间被节流约 180 次/次生成。这不是配置问题，是平台给的 CPU 配额，
**写不进 `cpu.max`、子 cgroup 也绕不过去、编译时也不会临时放宽**。

因此 `envconfig.py` 会读 `cpu.max` / CFS 配额 / CPU 亲和性，自动把线程数设成「实际可用核数」，
避免开出多余线程互相抢调度。检查当前配额：

```bash
awk '{printf "上限 %.2f 核\n", $1/$2}' /sys/fs/cgroup/cpu.max
```

**结论**：想更快，只有给机器更多 CPU 核数，或换有 GPU / AVX-512 / AMX 的机器；
在本仓库这套最小方案内部已无进一步提速空间。

需要手动指定线程数（例如绑定到 8 核）：

```bash
OMP_NUM_THREADS=8 ./start.sh 3000
```

## 8. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `make deps` 下载中断 | 直接重跑，支持断点续传；或用 `CACHE=` 指向已有文件 |
| `pip install` 报 wheel 平台不兼容 | 引擎 wheel 是 `manylinux_2_35_x86_64`，需 glibc ≥ 2.35；老系统请改用 Docker |
| numpy wheel 装不上 | 该 wheel 是 cp311，请用 Python 3.11；`make venv` 已内置在线回退 |
| `FileNotFoundError: 缺少 GGUF 权重` | 先 `make deps`；确认 `models/` 下两个文件名与上表一致 |
| 服务启动但生成很慢 | 看第 7 节的 CPU 配额；`nproc` 大不等于能用 |
| 端口被占用 | `make PORT=8080` |
| 想清空环境重来 | `make distclean` 删 venv（保留权重），再 `make setup` |
| 音频是静音 / 噪声 | 用第 6.2 节检查峰值与 RMS；异常时重新 `make deps` 校验权重完整性 |
| 9 个音色的名字 | `curl -s localhost:3000/api/info \| python3 -m json.tool` 看 `speakers` |

## 9. 二次开发入口

这套仓库刻意保持「薄」，方便往上加东西：

- **换模型/量化**：改 `app.py` 与 `synth.py` 里 `ROOT / "models" / ...` 两个文件名，
  并在 `fetch_deps.py` 的 `FILES` 里补上对应大小与 SHA-256。
- **加流式播放**：`synth.py` 已有 `generate_custom_voice_streaming` 示例，
  把它接到 `app.py` 的 worker 里，边生成边往客户端推 WAV 分片。
- **换界面**：只改 `index.html`，后端接口不变。
- **加鉴权 / 多实例**：`app.py` 是单文件标准库服务，改 `Handler` 即可；
  多实例靠 `PORT` 起多个进程，各自独立队列。

改完记得 `git status` —— 环境文件已被 `.gitignore` 排除，不会误提交。
